    Apple GPU (float32 mode)¶

    CERIDWEN runs on the GPU of an Apple Silicon Mac through jax-graft, which registers JAX's mtl platform. Apple GPUs have no float64, so on that backend CERIDWEN runs in float32 mode. This page says what to install, what the mode changes, what it guarantees and what it refuses.

    Install and run¶

    examples/apple_gpu_mock_fit.ipynb is the whole story in one notebook: a mock galaxy (photometry and a spectrum), its figure, a nested-sampling fit on the GPU and the recovered parameters against the input, with the priors shown next to the posteriors; about three and a half minutes on an M3 Pro. Four more notebooks go through the observation types one at a time: mock_fit_1_photometry.ipynb, mock_fit_2_photometry_lines.ipynb (adds line fluxes and the gas parameters), mock_fit_3_spectrum.ipynb (a spectrum alone: a per-pixel resolving power, a sampled velocity dispersion, emission lines) and mock_fit_4_spectrum_photometry.ipynb (a spectrum whose flux scale is a sampled nuisance, anchored by the photometry).

    pip install ceridwen installs jax-graft on an Apple Silicon Mac with macOS 26 and Python 3.12 or newer (the only platform jax-graft ships wheels for; the marker in pyproject.toml keeps older Macs and Python 3.11 on the CPU build). Nothing else is needed: jax-graft makes the GPU JAX's default backend, and import ceridwen sees that and switches the process to float32, with one warning of its own (JAX and tensorflow-probability add theirs, see "Known limits"):

    UserWarning: float32 mode: JAX's default backend is the Apple GPU (mtl), which has no float64.
Evidences, gradients and the sampler state are float32 (docs/mac_gpu.md); for a float64 fit
set JAX_PLATFORMS=cpu

    python -m ceridwen.check reports the two lines

      [ok  ] jax float64  -- off: float32 mode, chosen because the Apple GPU is JAX's default backend ...
  [ok  ] jax backend  -- mtl (mtl:0): Apple GPU via jax-graft, float32

    and every fitSED header prints Device : MTL (mtl:0) and Precision : float32. The result file records both: config/precision ("float32") and config/platform ("mtl").

    The environment switches:

    Environment Precision Device
    nothing set (jax-graft installed) float32 Apple GPU
    JAX_PLATFORMS=cpu float64 CPU, the same numbers as any other CPU
    CERIDWEN_X64=0 (any machine) float32 whatever JAX's default device is
    CERIDWEN_X64=1 with the GPU as default refused at import set JAX_PLATFORMS=cpu instead

    CERIDWEN_X64=0 on a CPU or CUDA machine is the same float32 mode without the GPU: useful to reproduce a Mac result elsewhere, not a precision to choose when float64 is available.

    What float32 mode changes inside the package¶

    The forward model, the likelihood and the samplers run unchanged in float32. Three things are done differently so that they survive it; all three are no-ops under float64, and the float64 compiled programs are byte-identical to 1.0.13 (T4: 21 445 arrays compared, none differ; the physical standard, scripts/physical_check.py: 1680 arrays, every output identical).

    Data rescaling at the observation layer. A spectrum in cgs F_nu has sigma ~ 1e-31, whose square underflows float32 (smallest normal number 1.2e-38), so every kernel that forms sigma^2, 1/sigma^2 or A^T W A would be wrong. ceridwen.likelihood.observation_data multiplies each observation's data, uncertainties and calibration vector by one power of two that brings its median uncertainty to order unity (exact: a power of two changes no mantissa bit), the noise model's jitter parameter (data units) is shifted by ln(scale), and the kernels run in those units. Their ln L is the true ln L minus ndof ln(scale), a constant of the observation; the sampler works in those units (adding ~1e6 inside a float32 kernel would quantise ln L to 0.1), and run_sampler / map_fit add the constant back, in float64 on the host, to the reported ln Z, ln L and MAP ln posterior. likelihood.float32_rescaling and likelihood.loglike_offset expose the numbers.

    No literal float64 on the device. ceridwen.precision.float_dtype() is the working dtype; every device array whose dtype the package chooses goes through it. Host-side NumPy stays float64 everywhere: the SSP grid axes, Z_sun resolution, provenance and the result file.

    Constants outside the float32 range. The ionising-photon table (L_sun / h = 5.8e59) is computed on the host in float64 and stored in the working dtype, and the 1e-70 floors of the metallicity and dust-emission kernels become the smallest normal float32.

    Refused in float32 mode, with the error saying so: Spectrum(marginalize_elines=True) (the line marginal forms A^T W A in flux units) and a noise model with a fixed numeric jitter (it cannot be rescaled with the data; sample it instead).

    What the mode guarantees¶

    tests/test_float32_parity.py runs the six golden configurations and a mock galaxy in physical units (SDSS photometry, a 600-pixel cgs spectrum with sigma ~ 1e-31, three line fluxes; nine free parameters) in float64, in float32 on the CPU and in float32 on the GPU, in separate processes. Measured on an M3 Pro (jax 0.11.2, jax-graft 0.0.5, 2026-10-15):

    Quantity float32 vs float64 Metal vs float32 CPU Metal run to run
    SSP weights W 3e-6 (step) / 5e-6 (linear) of the largest weight 2e-7 identical
    spectrum, continuum pixels 5e-6 relative 2e-7 identical
    spectrum, pixels under a nebular line up to 4e-4 relative (4e-5 of the peak) 2e-7 identical
    photometry (maggies) 2e-5 relative 9e-7 (mock), 3e-5 (golden 15000-pixel integrals) identical
    line fluxes 4e-6 relative 2e-7 identical
    ln posterior (true units) 4e-4 and 0.015 on values of 4e4 and 2e4 0.01 identical
    gradient 5e-5 of the largest component up to 6e-4 relative (three runs: 1e-5, 8e-5, 6e-4)

    The line-pixel error comes from evaluating the profile argument (lambda - lambda_0) / sigma in float32: at 1e4 Angstrom a float32 resolves 1e-3 Angstrom, so the profile wings move by that fraction of a pixel. It is a property of the mode, not of the GPU (the CPU float32 run shows the same numbers). The gradient varies run to run on the GPU because the transpose of the redshift interpolation is a scatter-add, which is atomic there; the forward model and ln L are byte-identical run to run.

    So: a float32 fit gives the same posterior as a float64 fit to well within the sampling error, and the same ln Z once the sampler is given twice the inner steps (see "Speed" below), but its numbers are not comparable bit for bit with a float64 fit, and two nested-sampling runs with the same rng_key are only identical on the CPU.

    Speed¶

    scripts/bench_mac_metal.py fits the parity mock with nested sampling in each mode and times the sampler's value-only ln L at its batch widths:

    python tests/baselines/_capture_f32.py --no-goldens ref.npz
JAX_PLATFORMS=cpu                python scripts/bench_mac_metal.py --mock-data ref.npz --out bench/f64_cpu
JAX_PLATFORMS=cpu CERIDWEN_X64=0 python scripts/bench_mac_metal.py --mock-data ref.npz --out bench/f32_cpu
                                 python scripts/bench_mac_metal.py --mock-data ref.npz --out bench/f32_mtl
python scripts/bench_mac_metal.py --compare bench/*/summary.json

    Measured on the M3 Pro (jax 0.11.2, jax-graft 0.0.5, 2026-10-15), nine free parameters, num_live 200, num_delete 40; us/point is the value-only ln L under vmap at the sampler's two batch widths (median of 200 calls, compile excluded):

    run inner steps ln Z calls wall us/point W=40 us/point W=200
    CPU float64, seed 0 30 40933.16 +- 0.36 168 000 1731 s 1550 1335
    CPU float64, seed 1 30 40933.21 +- 0.32 169 200 1879 s
    CPU float32, seed 0 30 40930.96 +- 0.40 180 000 1017 s 765 750
    Metal float32, seed 0 30 40931.88 +- 0.39 176 400 421 s 174 131
    Metal float32, seed 1 30 40932.04 +- 0.46 174 000 418 s
    Metal float32, seed 0 60 40933.77 +- 0.38 328 800 908 s

    The GPU evaluates the likelihood 9 to 10 times faster than the CPU in float64 and 4 to 6 times faster than the CPU in float32, and the whole fit runs 4 times faster than the float64 CPU fit (the sampler's own loop runs on the CPU side and is not sped up).

    The evidence needs more inner steps in float32. The two float64 seeds agree in ln Z to 0.05. Every float32 fit with the default 30 inner slice steps comes out 1.1 to 2.2 nats lower, 3 to 6 times the quoted error, on the CPU as on the GPU; with 60 inner steps the GPU fit returns 40933.77 +- 0.38, within the error of float64. The slice sampler mixes less well per step in float32 (cause not identified; the peak ln L agrees to 0.3 in every run), and nested sampling with incomplete mixing underestimates Z. Posterior means and widths of all six runs scatter alike: between the two float64 seeds the means move by up to 1.8 standard deviations and the widths by factors 0.3 to 1.7 (200 live points), and the float32 runs sit inside that scatter. Posterior constraints need no change.

    Do not compare evidences between runs of different precision or different num_inner_steps. A float32 ln Z sits 1 to 2 nats below a float64 ln Z of the same data at the same settings, and twice the inner steps moves it by the same amount. Bayes factors are only meaningful between fits made with the same precision, the same num_live, num_delete and num_inner_steps (fitSED records all of them in the result file: config/precision, config/platform and the sampler settings). Nothing is changed by default: the inner-steps default stays 30 in both precisions.

    scripts/mac_metal_probe.py times the 34 JAX operations CERIDWEN uses one by one on the CPU and the GPU and checks their values agree (all 34 do; the table is in its output).

    Known limits¶

    • jax-graft is at version 0.0.5 ("expect some sharp edges", its README). An operation it cannot compile fails at compile time with UNIMPLEMENTED: Metal: ...; report it with the fitSED header and python -m ceridwen.check.
    • tensorflow-probability's samplers ask for float64 internally and are truncated to float32, with UserWarning: Explicitly requested dtype float64 requested in ... is not available the first time a prior is drawn (several lines, from tfp's random_generators.py, numpy_array.py and ops.py, and one from jax/_src/numpy/array_methods.py). JAX itself prints Platform 'mtl' is experimental .... All of these are harmless. A large model can also make XLA print E... slow_operation_alarm.cc:73] Constant folding an instruction is taking > 1s: a compile-time message, not an error.
    • The nested sampler's progress bar shows ln Z in the rescaled units the sampler works in (above, "Data rescaling"), so it can differ from the final log Z by the constant ndof ln(scale), thousands of nats for a spectrum. The final value and the result file are in true units.
    • The nested sampler's inner loop is dispatched step by step; at small batch widths the GPU is slower than the CPU (see the benchmark), so the GPU pays off for wide batches and gradient-based samplers.
